RabbitMQ Quorum ×3가 하는 일

RabbitMQ는 오래 걸리는 OCR·ETL·RAG 작업을 API 요청에서 분리해 안전하게 줄 세우는 메시지 큐입니다. Quorum ×3는 메시지를 3개 RabbitMQ 노드에 복제해 1개 노드 장애에도 큐를 유지하려는 구성입니다.

1개 장애 허용

3개 중 2개가 살아 있으면 큐의 과반수가 남아 새 leader 선출과 메시지 처리가 가능합니다.

왜 큐가 필요한가

  • OCR·ETL·RAG 작업은 API 응답 시간보다 오래 걸릴 수 있습니다.
  • 요청이 몰려도 Worker가 처리 가능한 속도로 천천히 소비합니다.
  • Worker 장애 시 ack 되지 않은 메시지를 다시 처리할 수 있습니다.
  • 실패가 반복되는 작업은 DLQ로 보내 사람이 확인합니다.

왜 3개인가

  • Quorum은 과반수 합의가 핵심이라 홀수 구성이 유리합니다.
  • 1개는 HA가 없고, 2개는 1개 장애 시 과반수를 만들 수 없습니다.
  • 3개는 2/3 과반수를 유지해 1개 장애와 rolling update를 견딥니다.
  • 5개는 2개 장애까지 견디지만 초기 리움에는 비용과 지연 부담이 큽니다.

노드 수 비교

구성과반수장애 허용판단
1 node10개단일 장애점. 운영 quorum 목적에 맞지 않음
2 nodes2실질 0개1개가 죽으면 과반수 없음. 비용 대비 HA 이점이 작음
3 nodes21개운영 HA의 실용적 최소 구성. 리움 Production 기준
5 nodes32개더 강하지만 비용, 저장소, 복제 지연 증가
정리: RabbitMQ Quorum ×3는 RabbitMQ를 세 번 중복 표기한 것이 아니라, Production 메시지 큐를 3개 RabbitMQ Pod/Node에 복제해 운영 안정성을 확보한다는 뜻입니다. 리움에서는 문서 처리, OCR, RAG 적재, 리포트 작업이 한 번에 몰릴 수 있으므로 API와 Worker 사이에 durable queue, consumer ack, retry with backoff, DLQ를 둡니다. 3개는 1개 장애를 견디는 최소 운영형 quorum 구성이며, 더 큰 5개 구성은 실제 queue depth와 장애 요구가 커졌을 때 검토하면 됩니다.
