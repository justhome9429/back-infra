비Production 환경이 별도 NKS 클러스터인 이유

비Production은 운영 트래픽을 받지 않는 검증/개발 환경입니다. 리움은 Production, Validation, Development를 namespace만 나누는 방식이 아니라 NKS 클러스터 단위로 분리합니다.

Development

개발자 단위 테스트, 기능 구현, 빠른 실험을 위한 비용 절감 환경

Validation

배포 전 통합검증, 일부 부하검증, 모델 회귀평가

Release Gate

검증 통과 빌드만 운영 배포 대상으로 승격

Production

실 사용자 24×7, HA, 장애 대응 기준 환경

Production NKS

실제 기업·정부 사용
Multi-AZ 운영 기준

API 4/8 ×3 Worker 4/8 ×2 MQ 2/4 ×3 DB HA + Read Replica 24×7

Validation NKS

운영 반영 전 최종 검증
운영과 유사하지만 축소

App+Worker 4/8 ×2 단일 DB 2/8 ×1 통합검증 부하검증 일부 모델 회귀평가

Development NKS

개발과 단위 테스트
최소 비용 기준

App+Worker 2/4 ×2 단일 DB 2/8 ×1 개발 테스트 기능 실험 샘플 데이터

공통 CI/CD · NCR

같은 Docker 이미지를 환경별 NKS에 순차 배포

왜 별도 클러스터인가

  • 배포 실수가 Production으로 전파되는 것을 줄입니다.
  • 권한·Secret·네트워크 정책을 환경별로 분리합니다.
  • 검증 부하가 운영 Pod와 자원을 경쟁하지 않습니다.

Namespace만 나누면

  • 클러스터 장애나 설정 실수가 모든 환경에 영향을 줄 수 있습니다.
  • 운영/검증 권한 경계가 흐려집니다.
  • 부하 테스트가 같은 Control Plane과 Node 자원을 흔들 수 있습니다.

사양 차이를 둔 이유

환경기준이유
Validation4vCPU/8GB ×2운영 배포 전 통합검증과 일부 부하검증을 수행해야 하므로 Prod와 같은 4/8 노드 기준
Development2vCPU/4GB ×2개발·단위 테스트 중심이므로 비용을 줄인 최소 실행 기준
정리: 비Production 환경은 운영을 대체하는 작은 복사본이 아니라, 운영을 안전하게 만들기 위한 분리된 검증/개발 공간입니다. 리움은 Dev, Val, Prod를 각각 별도 NKS 클러스터로 두어 장애 전파, 권한 오설정, 배포 실수, 자원 경합을 줄입니다. 그래서 구조도에는 Production VPC를 크게 그리고, 오른쪽에 비Production 별도 NKS 클러스터를 축약해서 표시했습니다.
